# Development guide

Prerequisite: Node and pnpm compatible with the pinned package manager in `package.json`. Run `pnpm install`, then `pnpm dev`. Use `pnpm test` for the built-in test suite and `pnpm build` for the Astro production build; use `pnpm preview` to inspect the build. No lint, formatter, or standalone typecheck script exists today. `pnpm exec astro check` is available but currently reports 23 existing diagnostics, so it is informative rather than a passing gate. AWS Amplify runs `pnpm install --frozen-lockfile`, `pnpm build`, and publishes `dist/` as described in `amplify.yml`.

Assessment work belongs under `src/features/technology-health-assessment/`. Framework constants live under `methodology/framework/`; capability modules own methodology content; version assembly lives under `methodology/versions/`; the read model is a compatibility boundary; `lib/` contains current scoring, findings, confidence, and storage libraries. Use the [assessment platform roadmap](assessment-platform-roadmap.md) to plan work across all documented capabilities.

To add a capability, update the catalog, create the five module files, add the module to a version, validate, test, and update methodology/reference docs. To add a question, preserve its stable ID, define one concept, observable options, importance/severity, unknown behavior, evidence guidance, and any finding/recommendation references. To add findings, use capability-owned definitions and justify severity. To add recommendations, define actions, outcome, effort/window, and valid mapping IDs. To add a standards mapping, identify framework/version/publisher and a specific reference; note that current source/review fields are not yet modeled.

To create a methodology version, copy the version assembly pattern, classify the change under [versioning](../methodology/methodology-versioning.md), freeze the previous artifact if published, create a real hash, add compatibility fixtures, and update `active-methodology-version.md`. To test saved responses, use the storage shape in [persistence](../architecture/persistence-and-compatibility.md) and add a parse/migration contract test. Do not silently change `mvp-1` behavior.
